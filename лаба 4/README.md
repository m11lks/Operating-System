# Лабораторная работа №4. Синхронизация процессов и именованные каналы

Работа посвящена двум темам:

1. **Задача «читатели — писатели»**: несколько процессов-писателей и процессов-читателей работают с общим буфером из 12 страниц в разделяемой памяти. Доступ к каждой странице синхронизируется семафорами, ход работы каждого процесса пишется в лог.
2. **Межпроцессный обмен через именованный канал** (named pipe) с асинхронным (перекрывающимся) вводом-выводом.

## Состав

| Файл | Платформа | Что делает |
|---|---|---|
| [`disp.cpp`](disp.cpp) | Windows (Win32 API) | Диспетчер: запускает заданное число писателей и читателей и ждёт их завершения |
| [`lab4_writer.cpp`](lab4_writer.cpp) | Windows (Win32 API) | Писатель: создаёт общую память и семафоры, пишет сообщения в свободные страницы |
| [`lab4_reader.cpp`](lab4_reader.cpp) | Windows (Win32 API) | Читатель: открывает общую память и семафоры, читает заполненные страницы |
| [`lab4_server.cpp`](lab4_server.cpp) | Windows (Win32 API) | Сервер именованного канала: асинхронная запись с ожиданием события |
| [`lab4_client.cpp`](lab4_client.cpp) | Windows (Win32 API) | Клиент именованного канала: асинхронное чтение с completion-процедурой |

> Linux-реализации этой лабораторной в репозитории нет, все файлы написаны под Win32 API.

## Часть 1. Читатели и писатели

### Общие ресурсы

| Ресурс | Имя | Назначение |
|---|---|---|
| Проецируемая память | `Local\mapping_file` | Буфер из 12 страниц по 4096 байт (`CreateFileMapping` поверх файла подкачки) |
| Семафоры записи | `Local\sema_write_0` … `_11` | Начальное значение 1: страница **свободна**, в неё можно писать |
| Семафоры чтения | `Local\sema_read_0` … `_11` | Начальное значение 0: страница **заполнена**, её можно читать |

У каждой страницы своя пара семафоров. Страница всё время находится ровно в одном из двух состояний: «свободна» или «заполнена».

### Писатель (`lab4_writer.cpp`)

1. Создаёт (или открывает уже созданные) семафоры и проецируемую память, отображает её (`MapViewOfFile`) и фиксирует в ОЗУ (`VirtualLock`).
2. 12 раз повторяет цикл:
   - ждёт **любую** свободную страницу: `WaitForMultipleObjects(write_sem, bWaitAll = FALSE)`; индекс сработавшего семафора даёт номер страницы;
   - пишет в страницу строку `Data from Writer PID <pid>, Iteration <i>`;
   - «работает» случайное время 0,5–1,5 с;
   - помечает страницу заполненной: `ReleaseSemaphore(read_sem[page])`.
3. Каждое состояние (`Start waiting`, `Writing | Page N`, `Moving to release`) пишется с меткой времени `timeGetTime()` в файл `writer_<PID>.log`.

### Читатель (`lab4_reader.cpp`)

Работает зеркально: ждёт любой из `read_sem`, читает страницу, выдерживает паузу 0,5–1,5 с и освобождает её через `write_sem[page]`. Лог пишется в `reader_<PID>.log`. Если ни одного писателя ещё нет и объекты не созданы, читатель завершается с ошибкой.

### Диспетчер (`disp.cpp`)

- Запрашивает число писателей и читателей.
- Запускает их через `CreateProcessA` с флагом `CREATE_NO_WINDOW`: процессы работают в фоне без своих консолей. Сначала стартуют писатели, чтобы объекты синхронизации уже существовали к запуску читателей.
- Ждёт завершения всех процессов: `WaitForMultipleObjects(..., bWaitAll = TRUE, INFINITE)`.

### Сборка и запуск

MinGW (нужна `winmm` для `timeGetTime`):

```bash
g++ lab4_writer.cpp -o lab4_writer.exe -lwinmm
```

```bash
g++ lab4_reader.cpp -o lab4_reader.exe -lwinmm
```

```bash
g++ disp.cpp -o disp.exe
```

В MSVC библиотека подключается сама через `#pragma comment(lib, "winmm.lib")`.

Все три `.exe` должны лежать в одной папке. Запускается `disp.exe`, а после завершения по файлам `*.log` можно построить временную диаграмму состояний процессов.

> Каждый писатель делает 12 записей, каждый читатель 12 чтений. Если читателей больше, чем писателей, лишние читатели не дождутся данных и диспетчер зависнет. Удобнее всего запускать поровну.

## Часть 2. Именованный канал

Сервер и клиент обмениваются сообщениями через канал `\\.\pipe\npipe`. Обе стороны используют **перекрывающийся ввод-вывод**, но двумя разными способами.

### Сервер (`lab4_server.cpp`): ожидание через событие

| Пункт | Действие | Функции |
|---|---|---|
| 1 | Создать канал | `CreateNamedPipe` (`PIPE_ACCESS_OUTBOUND \| FILE_FLAG_OVERLAPPED`, режим сообщений), `CreateEvent` (ручной сброс) |
| 2 | Дождаться клиента | `ConnectNamedPipe` |
| 3 | Записать строку | `WriteFile` со структурой `OVERLAPPED`. При `ERROR_IO_PENDING` сервер ждёт `WaitForSingleObject(ovrlap.hEvent)` |
| 4 | Отключить клиента | `DisconnectNamedPipe` |
| 5 | Выход | `CloseHandle` |

### Клиент (`lab4_client.cpp`): completion-процедура

| Пункт | Действие | Функции |
|---|---|---|
| 1 | Подключиться к каналу | `CreateFile("\\\\.\\pipe\\npipe", GENERIC_READ, ..., FILE_FLAG_OVERLAPPED)` |
| 2 | Прочитать сообщение | `ReadFileEx` с callback-функцией `FileIOCompletionRoutine`, затем `SleepEx(INFINITE, TRUE)` |
| 3 | Выход | `CloseHandle` |

`ReadFileEx` сразу возвращает управление. Когда данные приходят, система ставит `FileIOCompletionRoutine` в очередь APC потока. Процедура выполняется, только пока поток находится в **тревожном ожидании** (`SleepEx` с `bAlertable = TRUE`), и выводит полученную строку.

### Сборка и запуск

```bash
g++ lab4_server.cpp -o lab4_server.exe
```

```bash
g++ lab4_client.cpp -o lab4_client.exe
```

Порядок такой:

1. сервер: пункт 1 (создать канал), пункт 2 (ждёт подключения);
2. клиент: пункт 1 (подключиться);
3. сервер: пункт 3, ввести строку;
4. клиент: пункт 2, строка выводится из completion-процедуры.
